================================================================================
PROMPT
================================================================================

You are extracting a structured mathematical knowledge graph from one chapter
of a {SOURCE_TYPE}. Read the chapter carefully, then produce a JSON object
with all mathematical content organized as typed nodes and directed edges.

INPUT:
  Book/paper ID: {BOOK_ID}
  Chapter number: {CHAPTER_NUM}
  Chapter title: {CHAPTER_TITLE}
  Source type: {SOURCE_TYPE}

{CHAPTER_TEXT}

================================================================================
0. MATHEMATICAL OBJECTS TO EXTRACT
================================================================================

Extract every instance of the Level-1 object types listed below. Two
additional Level-2 sub-block types (`proof_step`, `algorithm_step`) are
OPTIONAL and emitted only when fine-grained granularity is explicitly
requested by the caller (see Section "Granularity" below). Default:
extract Level 1 only.

  Direction convention: arrow A → B means "A supports B" / "B depends on A".
  Edge name reads as "B [name] A" (target's action on source).

  Never create both `uses` and `generalizes` between the same pair.
  Use the more specific type when applicable.


================================================================================
0b. SOURCE-TYPE-SPECIFIC GUIDANCE
================================================================================

--- If {SOURCE_TYPE} = "textbook" ---

  - EXAMPLES and EXERCISES are a major part of the content. Extract every
    numbered example and exercise individually — they are pedagogical gold.
  - Exercise sections often appear at chapter end. Extract each exercise
    as a separate node, not one big "exercise set" node.
  - If exercises have SOLUTIONS (inline or in appendix), extract the
    solution as the exercise node's raw_text. If the solution is a proof,
    create a separate proof node linked to the exercise.
  - Theorems may be stated WITHOUT PROOF ("proof omitted", "left as
    exercise"). That is fine — create the theorem node without a proof
    node. If "proof left as exercise", create an exercise node linked via
    "tests" to the theorem.
  - Historical remarks, biographical notes, and "Remark:" blocks are
    common. Extract as REMARK nodes.
  - Cross-references like "by Theorem 3.14 from Chapter 2" — create a
    "uses" edge to the node ID from Chapter 2 (e.g., b006_ch02_thm14).

--- If {SOURCE_TYPE} = "paper" ---

  - RIGOR: for math and CS-theory papers, most nodes are rigor="formal"
    (the default — you can omit the field). For stat.ML / applied papers,
    use rigor="semi_formal" or "numerical" as appropriate. For proofs that
    are sketches, set rigor="semi_formal" on the proof node.

  - STATISTICAL / ML PAPERS often present mathematical content that is NOT
    in theorem-proof form. Common pattern:
      (1) Define a statistical MODEL (e.g., mixture of Gaussians, LDA,
          diffusion model) → extract as definition with subclass="model"
      (2) Define a LIKELIHOOD or LOSS FUNCTION → extract as definition
          with subclass="loss_function", or as equation
      (3) Define an ESTIMATOR (e.g., MLE, MAP) → extract as definition
          with subclass="estimator". If presented as "find θ maximizing
          ℓ(θ)", also extract as problem with subclass="optimization"
      (4) Give an ALGORITHM (EM, MCMC, variational inference) → extract
          as algorithm with subclass and complexity. Link to problem via
          "solves" edge.
      (5) Prove consistency / convergence → extract as theorem
      (6) Apply to data → extract as example with subclass="applied"
    The statistical model IS a definition — it defines a mathematical
    object (a family of distributions). It is often the paper's primary
    contribution even though it is not a theorem.

  - THEORETICAL PHYSICS papers: most results are heuristic.
    * NEVER use type="theorem" unless the paper EXPLICITLY labels it
      "Theorem". Use type="claim" with rigor="heuristic" for unproved results.
    * Lagrangians, Hamiltonians, actions, partition functions → definition/model
    * Approximation methods (saddle-point, WKB, replica, mean-field) →
      proof with subclass="heuristic" and rigor="heuristic"
    * "To leading order in 1/N..." or "neglecting higher-order terms" →
      claim with rigor="heuristic"
    * Feynman diagram arguments → proof/heuristic
    * Numerical results / simulations → example/computational with rigor="numerical"

  - MATHEMATICAL BIOLOGY papers:
    * ODE/PDE models (SIR, Lotka-Volterra, reaction-diffusion) → definition/model
    * Stability analysis, fixed-point analysis → if proved: theorem; if
      argued: claim with rigor="semi_formal"
    * Simulation results → example/computational with rigor="numerical"
    * "Assuming large population..." → note rigor="heuristic" when the
      limit is not justified rigorously

  - ENGINEERING / SIGNAL PROCESSING papers:
    * Transfer functions, frequency responses → definition/operator
    * Design criteria (SNR, BER, capacity) → definition/metric
    * Performance bounds → claim/bound with rigor="semi_formal" unless proved
    * Algorithms (FFT, Kalman, beamforming) → algorithm with complexity
    * Shannon-type theorems → theorem with rigor="formal" (genuinely proved)

  - PROOFS are the primary content alongside theorems. Extract every proof
    with its full text.
  - EXAMPLES are rare in research papers. When present, they are usually
    important — extract them.
  - EXERCISES are almost never present. Skip unless explicitly labeled.
  - Papers often use heavy CUSTOM MACROS (\newcommand). Expand all custom
    macros to standard LaTeX in statement_latex (see Rule 5d below).
  - Cross-references use citations: "by [CT05, Theorem 1]". When possible,
    create a "uses" edge. If the cited result is from another paper not in
    our corpus, add a note in the edge or skip.
  - ALGORITHMS are common in CS/ML papers. Extract with full pseudocode.
  - The paper's introduction often restates main results informally before
    formal versions appear later. Extract only the FORMAL version (the one
    with a Theorem/Lemma label), not the informal preview.


================================================================================
EXTRACTION RULES
================================================================================

1. NODE TYPES — DETAILED GUIDANCE:

   DEFINITION     — formal or semi-formal introduction of a named concept.
                    Includes "\begin{definition}", "We define X as...",
                    "Let X be a...", "X is called... if...".
                    Does NOT include ephemeral notation shortcuts like
                    "write f for f(x)" — those are notation, not definitions.

   THEOREM        — labeled or numbered theorem.
   LEMMA          — labeled or numbered lemma.
   PROPOSITION    — labeled or numbered proposition.
   COROLLARY      — labeled or numbered corollary.
   CLAIM          — informal claim, "Fact", "Observation" with a statement.
   CONJECTURE     — unproven claim explicitly labeled as conjecture.

   PROOF          — proof of a theorem/lemma/proposition/corollary.
                    Link to its parent via a "proves" edge.

   EXAMPLE        — worked example illustrating a concept.
                    Link to the concept via an "illustrates" edge.

   EXERCISE       — problem for the reader (with or without solution).
                    Link to the relevant concept via a "tests" edge.

   EQUATION       — explicitly labeled/numbered equation (not every inline
                    formula — only equations that the paper references by
                    number, e.g., "by equation (3.5)").

   ALGORITHM      — pseudocode or step-by-step procedure.

   REMARK         — author's remark, note, observation that adds context
                    but is not a theorem or definition.

   PROBLEM        — a NAMED OR FORMULATED FORMAL mathematical problem the
                    paper studies. Optimization formulations, decision
                    problems, named problems with attached algorithms /
                    complexity / hardness. NOT for unsolved questions —
                    those are OPEN_PROBLEM.

   OPEN_PROBLEM   — an unsolved mathematical question with no known
                    solution; e.g. "Open Problem: Are there infinitely
                    many odd perfect numbers?", the Riemann Hypothesis
                    posed as a question. Similar to CONJECTURE in spirit
                    but content-wise more like a question without a
                    stated answer.

   ASSUMPTION     — a `\begin{assumption}` block declaring standing
                    assumptions for a section / theorem cluster.
                    "Assumption (A1): f is convex." → assumption node.
                    NOT the per-theorem `assumptions` field.

   PROOF_STEP     — (Level 2, OPTIONAL) one logical move within a proof.
                    Set `parent_id` to the parent PROOF node ID. Emit
                    only at `with_proof_steps` granularity.

   ALGORITHM_STEP — (Level 2, OPTIONAL) one numbered pseudocode line
                    within an algorithm. Set `parent_id` to the parent
                    ALGORITHM node ID. Emit only at fine-grained
                    algorithm granularity.

   Skip: section headings, figure captions, bibliographic references,
   acknowledgments, table of contents entries.

2. NODE FIELDS (for each extracted node):

   {
     "id":       unique ID, format: "{BOOK_ID}_ch{NN}_{type_abbrev}{seq}",
                 e.g. "b006_ch03_def01", "b006_ch03_thm05", "b006_ch03_proof05"
                 Type abbreviations: def, thm, lem, prop, cor, claim, conj,
                 proof, ex, exer, eq, alg, rem, prob, open_prob, assum,
                 pstep, astep

     "type":     one of (Level 1, 16 types):
                 definition, theorem, lemma, proposition, corollary,
                 claim, conjecture, proof, example, exercise, problem,
                 open_problem, equation, algorithm, remark, assumption.
                 Plus (Level 2, optional, 2 types): proof_step, algorithm_step.

     "rigor":    how rigorous the justification is (orthogonal to type):
                 formal       — precise statement + rigorous proof
                 semi_formal  — precise statement + proof sketch / "standard arguments"
                 heuristic    — justified by physical/intuitive argument, not proved
                 numerical    — supported by simulation/computation only
                 conjectural  — stated without justification
                 (null if clearly formal, which is the default for math papers)

     "subclass": optional finer categorization. Values depend on type:
                 definition:    concept | model | estimator | loss_function | metric | notation
                 theorem:       existence | uniqueness | convergence | bound | characterization | equivalence | impossibility
                 proof:         direct | contradiction | induction | construction | probabilistic | algebraic
                 algorithm:     exact | approximation | heuristic | randomized | greedy | iterative
                 problem:       optimization | decision | search | counting | estimation | feasibility | enumeration
                 open_problem:  famous | named | folklore
                 example:       illustrative | counterexample | computational | applied
                 exercise:      computational | theoretical | proof_exercise
                 equation:      identity | inequality | recursion | differential
                 assumption:    standing | regularity | structural | distributional | asymptotic
                 (null if unclear — don't guess)

     "tags":     OPTIONAL list[str] of type-specific tags drawn from a
                 controlled vocabulary (see TAGS_VOCABULARY in
                 src/node_types.py). Validators warn but do NOT reject
                 unknown values, so emit only tags you are confident in.
                 Example: a theorem proving a bound → tags: ["bound"];
                 an iterative approximation algorithm → tags: ["iterative",
                 "approximation"].

     "origin":   provenance of the node (default "paper"):
                 paper     — node represents a contribution introduced by
                             THIS paper (definition, theorem, algorithm,
                             example, etc. that the paper establishes).
                 external  — node represents a CITED PRIOR RESULT the paper
                             invokes but does not establish (a classical
                             theorem like "Sinkhorn 1967", a baseline
                             algorithm used for comparison, a foundational
                             definition the paper depends on, etc.).
                 If omitted, defaults to "paper".

     "origin_citation": for origin="external" nodes ONLY, a free-text
                 citation string identifying the cited source.
                 Examples: "Sinkhorn 1967", "Cover & Thomas, Elements of
                 Information Theory", "Villani 2009, §6.1", "[CT05, Thm 1]".

     "name":     short descriptive name. Use the paper's own name if given
                 (e.g., "Cauchy-Schwarz inequality", "k-means algorithm").
                 If unnamed, write a short description
                 (e.g., "Convergence of gradient descent").

     "label":    the paper's own numbering, e.g., "Theorem 3.14",
                 "Definition 2.1", "Algorithm 4.1". Preserve exactly as
                 printed. null if unnumbered.

     "statement_latex":
                 the mathematical content in LaTeX. For theorems, this is the
                 full statement (assumptions + conclusion together).
                 Math MUST be wrapped in $..$ (inline) or $$...$$ (display).
                 Preserve original LaTeX commands — do NOT simplify or rewrite.

     "statement_clean":
                 same content with LaTeX commands stripped to readable English.
                 e.g., "$\|x\|_2 \leq C$" → "the L2 norm of x is at most C"

     "assumptions":  (for theorem-like nodes ONLY)
                 list of strings, each a separate hypothesis.
                 e.g., ["$f$ is continuous on $[a,b]$", "$f(a) < 0 < f(b)$"]

     "conclusions":  (for theorem-like nodes ONLY)
                 list of strings, each a separate conclusion.
                 e.g., ["there exists $c \\in (a,b)$ such that $f(c) = 0$"]

     "raw_text": the full original text block as it appears in the source.
                 Preserve verbatim — this is the recovery field.

     "page":     page number (integer) if extracting from PDF. null if from
                 LaTeX source without page numbers.
   }

3. ASSUMPTION / CONCLUSION SEPARATION:

   This is critical for downstream alignment. For every theorem, lemma,
   proposition, corollary, claim, and conjecture:

   - ASSUMPTIONS are conditions, hypotheses, setups:
     "Let...", "Suppose...", "Assume...", "Given...", "If...",
     "For every... satisfying..."

   - CONCLUSIONS are results, claims, what follows:
     "Then...", "There exists...", "We have...", "It holds that...",
     "...is at most...", "...converges to...", "...is unique"

   - If the statement is a single sentence with "If P then Q" structure:
     assumptions = ["P"], conclusions = ["Q"]

   - If the separation is unclear, put the FULL statement in conclusions
     and leave assumptions empty. Do NOT guess.

   - A statement like "The chromatic number of G is at most k" is a
     CONCLUSION, not an assumption — even though it contains no trigger
     word like "then".

4. EDGES (relationships between nodes):

   {
     "source": source node ID,
     "target": target node ID,
     "type":   one of: uses, proves, solves, illustrates, tests, generalizes, specializes
   }

   Edge types (arrow A → B, reads "B [type] A"):
     "uses"         — B uses A. Generic dependency: B's statement or proof
                      references A. Default when no specific semantic
                      relationship applies.
     "generalizes"  — B generalizes A. B has weaker assumptions or broader
                      scope. Subtype of "uses" — implies dependency.
                      Don't also create a "uses" edge for the same pair.
     "specializes"  — B specializes A. B is a special case (stronger
                      assumptions). Subtype of "uses".
     "proves"       — B proves A. B is the proof, A is the theorem.
                      Every proof should have exactly one "proves" edge.
     "solves"       — B solves A. B is an algorithm, A is the problem it
                      addresses. Parallels "proves" for algorithms.
     "illustrates"  — B illustrates A. B is an example of concept A.
     "tests"        — B tests A. B is an exercise about concept A.

   Algorithm extra fields (when extractable):
     "solves":              ID of the problem node (like proof's "proves")
     "approximation_ratio": e.g. "1.5", "O(log n)", null if exact
     "complexity":          e.g. "O(n^2)", "O(m log m)"

   Problem extra fields (when extractable):
     "complexity_class":    "P" | "NP-hard" | "NP-complete" | "PSPACE" | "unknown"
     "approximability":     "PTAS" | "FPTAS" | "APX-hard" | null

   Rules:
     - Only backward or same-chapter edges. No forward references to later
       chapters.
     - Target must be a node ID that exists in this or a previous chapter.
     - Prefer fewer confident edges over many speculative ones.
     - A proof's "uses" edges should list the key lemmas/definitions it
       invokes, not every symbol it mentions.

5. SELF-CONTAINED STATEMENTS (important for downstream matching):

   Each node's statement_latex and statement_clean should be understandable
   WITHOUT reading the rest of the paper. Specifically:

   a) NOTATION SIMPLIFICATION: if the paper says "we omit subscript i
      throughout" or "to simplify, we write X for X_i", EXPAND the notation
      back to its full form in the extracted statement. The reader of the
      JSON should not need the paper's notation section.

   b) IMPLICIT CONTEXT: if a theorem says "Under the conditions of
      Theorem 3.1, ..." — expand: state what those conditions are, or at
      minimum add a "uses" edge to Theorem 3.1.

   c) ABBREVIATIONS: if the paper defines "RIP" = "Restricted Isometry
      Property" in the introduction and then uses "RIP" throughout —
      the FIRST occurrence in each node should spell it out:
      "Restricted Isometry Property (RIP)". Subsequent occurrences in the
      same node can use "RIP".

   d) CUSTOM MACROS: if the paper defines \newcommand{\norm}[1]{\|#1\|}
      and uses \norm{x}, the extracted statement_latex should contain
      $\|x\|$, not $\norm{x}$. Expand custom macros to standard LaTeX.

6. WHAT NOT TO EXTRACT:

   - Inline formulas that are not part of a labeled/numbered structure
     (e.g., "where $n$ is the sample size" is NOT a definition node)
   - Section headings, paragraph titles
   - Figure/table descriptions (unless they contain a labeled equation
     or algorithm)
   - Bibliographic references, acknowledgments
   - Repeated statements (if the same theorem is stated twice, extract once)

6b. TYPE-PROMOTION RULE — content trumps environment:

   A node's type is determined by its SEMANTIC CONTENT, not the surrounding
   LaTeX environment. The environment is a hint; the content decides.

   Specifically:
     - A "\begin{definition}" block whose body is an OPTIMIZATION
       FORMULATION (e.g., "find x* = argmin f(x) subject to Ax <= b", or a
       named problem with attached algorithms / complexity / hardness) MUST
       be typed as PROBLEM, not DEFINITION. Diagnostic: does the object
       come with the recurring problem-attachments (algorithms that solve
       it, complexity discussion, dual formulation, hardness results)?
       If yes -> type="problem", typically subclass="optimization".
     - A "\begin{definition}" block whose body is a step-by-step procedure
       MUST be typed as ALGORITHM.
     - A "\begin{lemma}" or "\begin{proposition}" whose body is a numerical
       bound used as scaffolding for one theorem REMAINS as lemma /
       proposition (the environment captures the author's intent here).

   This is the "Type-promotion rule" from the manuscript appendix
   (node_types_appendix_draft.tex).

6c. CITED PRIOR RESULTS — extract as origin="external" nodes:

   Mathematical papers depend on cited prior results. A graph that captures
   only the paper's OWN contributions is missing its scaffolding. You MUST
   extract the cited classical theorems, foundational definitions, and
   baseline algorithms that the paper INVOKES but does not establish.

   What to extract as origin="external":
     - Classical theorems the paper cites and uses ("by Sinkhorn 1967",
       "by the Cover-Thomas information inequality", "Villani §6.1 shows
       that ...").
     - Foundational definitions from cited sources that the paper relies on.
     - Baseline algorithms the paper compares against (e.g., a network
       simplex method as a baseline for an optimal-transport algorithm).

   Format:
     - Use the SAME node types (theorem, lemma, definition, algorithm, ...)
       as for paper-internal nodes.
     - Set "origin": "external".
     - Set "origin_citation" to a short free-text identifier of the source.
     - Use "uses" edges to connect the external node to whatever paper-
       internal node depends on it.

   EXAMPLE 1 (cited classical theorem):

     {
       "id": "TP5.3",
       "type": "theorem",
       "name": "Information-Theoretic Inequality",
       "section": "3.1 (cited)",
       "statement": "For all $r,c \\in \\Sigma_d$ and $P \\in U(r,c)$: $h(P) \\leq h(r) + h(c)$, with equality iff $P = rc^T$.",
       "origin": "external",
       "origin_citation": "Cover & Thomas, Elements of Information Theory"
     }

   EXAMPLE 2 (baseline algorithm cited for comparison):

     {
       "id": "AP5.2",
       "type": "algorithm",
       "name": "Network Simplex Method for OT",
       "section": "2.2 (cited)",
       "statement": "Combinatorial LP solver for optimal transportation with worst-case complexity $O(d^3 \\log d)$.",
       "origin": "external",
       "origin_citation": "Ahuja, Magnanti, Orlin 1993"
     }

   When in doubt: if the paper says "by X", "as shown in [REF]", "we use
   the classical result of Y", or "we compare against the baseline Z",
   that is an external node.

7. QUALITY CHECKS (verify before returning):

   - Every proof node has exactly one "proves" edge
   - Every example node has at least one "illustrates" edge
   - No edge references a nonexistent node ID
   - No forward references to later chapters
   - Node IDs are unique
   - Assumptions and conclusions don't overlap (same text in both lists)
   - statement_latex has $..$ around all math
   - Every node has either origin="paper" (default) or origin="external"
   - Every origin="external" node has origin_citation populated
   - Optimization formulations (even inside \begin{definition}) are typed
     as PROBLEM, not DEFINITION (see rule 6b: type-promotion)
